# Aethel language specification and engineering plan

## 1. Language and scope

Aethel combines Gleam-style syntax and Python-style readability with strict evaluation, algebraic data types, and explicit mutation. The programmer defines logical values and access contracts. The compiler chooses a representation that satisfies those contracts and preserves observable behavior.

The sequential core has named functions, typed lambdas and scoped callbacks, rank-one parametric polymorphism, records, tagged sums, exhaustive pattern matching, finite lists and collections, local handles and views, and returned views rooted in caller parameters. Ordinary module functions such as `Option.map`, `Result.and_then`, and `Collection.fold` provide reusable behavior. User-defined type classes, higher-kinded types, implicit laziness, borrowed values stored in the heap, general threading, atomics, async, and unrestricted FFI are outside this core.

A function signature records parameter and result types, path effects, and allowed returned origins. The surface form `Collection(Entity) ~>.{pos, vel}` constrains access to the named paths. Internally distinguish reads, writes, and invalidation. Check declared effects against the body and against actual call arguments. Mutation of a constructor requires authority over the whole sum.

## 2. Functional semantics and ownership

Use a typed call-by-value lambda calculus. Evaluate arguments before applying a function. The declarative judgment distinguishes bindings that may be freely reused from affine resources. Moving an owner consumes the binding, and dropping runs its specified cleanup once. A pair constructor may duplicate a copyable integer. Duplicating a unique buffer requires an explicit clone. A closure that consumes an owner from its environment is callable once. Scope any borrowed captures to their source view and forbid borrowed closures escaping in the first core. Retain the separate supported case of a named function returning a caller-rooted view.

Generalize rank-one type variables at immutable resource-independent value bindings and named functions. A mutable cell has one element type across all uses. Reject incompatible instantiations of a single allocated cell. Instantiate polymorphic functions at calls. No implicit polymorphic recursion is required.

In the pure, total, freely copyable fragment use extensional equality on logical values. Prove identity and associativity of composition and identity/composition for concrete combinators such as `Option.map`. These laws draw on mixed linear and nonlinear semantics. Resource operations use ownership-preserving composition and explicit drop effects. Any law about effects states which observations it compares. [Benton's categorical model](https://www.cl.cam.ac.uk/techreports/UCAM-CL-TR-352.html)

## 3. Borrow checking and branch facts

- Give each allocation a fresh provenance identity. A handle is an owner-rooted field/index/slice path with access authority. Multiple handles can target one place and alternate sequential accesses.
- A scoped shared reservation permits other reads. An exclusive reservation prevents conflicting accesses through other handles. Establish compatibility over physical read/write footprints, including packed updates. Reborrowing suspends the relevant parent permissions until release. The first structured record model gives an unscoped field access a view lasting one operation. A scoped child reuses a subset of its parent’s byte reservations with a restricted path and access mode. The parent’s authority resumes at the continuation. Permit disjoint sibling access. End views at their last use when liveness proves it safe.
- Destroying, relocating, or replacing a value invalidates affected descendant handles and requires the relevant views to have ended. Calls propagate invalidation and returned-origin summaries. Returned origins must remain live and within caller authority.
- Compare an exclusive-only policy and the aliasable-handle policy against shared semantics and named fixtures. Use exact regular expressions over resolved steps for reachability. Prove derivative correctness, graph coverage, and graph-transfer soundness. Conservative symbolic overlap must overapproximate possible concrete overlap. Different prefixes can lead to identical residuals, so prove disjointness on full concrete paths and footprints.
- Track bounds and equalities/disequalities on captured SSA values. A dominating `i != j` guard plus valid bounds may separate element borrows. Use half-open slices, including valid empty slices. Intersect facts at joins, invalidate unsupported facts, and check loop invariants. Start with a small certified arithmetic fragment and reject unknown proof obligations. Machine arithmetic must establish freedom from wraparound before using mathematical index facts.

## 4. Layout and physical execution

Use Zig-style arbitrary-bit-width integer names (`u1..u65535` unsigned, `i1..i65535` signed) alongside compiler-synthesized ranges (`IntInference`). The suffix counts logical **bits**, so `i7` is signed 7-bit, `u8` is eight bits, and `i24` is signed 24-bit (capped at `65535` bits; addressable natural alignment caps at 16 bytes, while FFI scalars and L1-cache-friendly hot fields remain machine/vector sized). When an expression's integer width is omitted, interval range propagation synthesizes the provably minimal `IntegerType`. Plain `+`, `-`, and `*` forbid silent runtime overflow via compile-time interval checking and guard narrowing, while saturating (`+|`, `-|`, `*|` -> `clampToType`), wrapping (`+%`, `-%`, `*|` -> `wrapToType`), and fallible (`Option` / `Result`) operations provide explicit overflow policies. Literal elaboration checks range, and signed values use two's complement. Width and signedness participate in type equality. [Zig integer naming and representation](https://ziglang.org/documentation/0.17.0/#Integers)

The target supplies byte size and alignment for addressable integer slots. Validate that the slot can contain the logical payload, its alignment is a power of two, and its stride preserves alignment for consecutive elements. Packed sub-byte fields (`1..=7` bits) share storage bytes via first-fit-decreasing bin packing when the co-borrow layout policy permits it. An independently addressable `u1` or `i7` occupies at least one byte. Group packing still follows physical access footprints. Record placement aligns the offset according to the slot, and access checks also require a valid allocation base and bounds. [Zig storage size](https://ziglang.org/documentation/0.17.0/#sizeOf)

Use a target descriptor with address-space limits, endianness, scalar sizes, alignments, and access conventions. Define a representation relation between a logical value and live physical memory. Check field extent, tag validity, initialization, alignment, and address arithmetic. Prove allocation, read, write, frame, and destruction simulation for AoS and SoA. Fix representation at allocation. Opaque calls reconstruct logical values when the required representation differs.

Lay out finite inline records bottom-up. Compare declaration-order placement against an alignment-sorted candidate with eligible fields packed. Prefer the smaller aligned size and use declaration order on ties. Preserve logical field indices for nested access. Place scalar fields deterministically in descending supported alignment with a stable tie-break. Within a fixed storage group, pack sub-byte widths 4, 2, and 1 in descending order. The restricted minimum compares layouts with the same storage-group partition, compatible power-of-two alignments and scalar sizes divisible by their alignment. Compare with the rounded-up sum of scalar bytes and separately rounded-up packed-group bytes. General layouts require correctness. A `Status` example has a two-bit tag and up to four payload bits, with a separate logical active flag.

Masked sequential updates preserve sibling bits. A setter's physical footprint includes its containing byte. Never pack independent elements into one byte. Separate conflicting fields when independent access requires it. Reject incompatible forced layout annotations. A column can be allocated at 64-byte alignment, and each scalar/vector access must independently establish alignment and bounds. Preserve strict floating-point behavior across the vector body and scalar tail. Fusion requires a source operation or policy that permits it.

Choose AoS or SoA per allocation site using loop field affinity, frequency or trip estimates, and reconstruction cost. Provide explicit layout overrides and explain the choice. Benchmark the heuristic independently from layout correctness.

## 5. Total computations and explicit outcomes

Ordinary functions terminate on valid finite inputs. Infer structural decreases over finite inductive data. For `while`, mutual recursion, and other recursion, require a checked well-founded measure over the actual transition, including calls through higher-order arguments. Accept user-supplied `decreases` evidence. Preserve source locations in diagnostics and report the unproved obligation if search stops. Prohibit general recursive value bindings, including cyclic strict lists.

A bounded search may return `Found`, `Finished`, or `Pending` with owned resumable state. A long-lived application uses a driver that waits for input between terminating `step(state, event)` calls. State transferred out of each step owns its data. Release step-local reservations before returning. Model event delivery as an external interaction. A later explicit stream extension must prove finite progress per observation and prevent borrowed values escaping a step. Filtering a stream with an always-false predicate illustrates why a bounded result count does not bound the work.

Give checked operations explicit outcomes such as `Option` or `Result`. A proved in-bounds access can use a direct result type. Apply the same policy to invalid divisors, overflow, allocation failure, and supported I/O errors. Accepted core computations finish with a value of the declared type under valid inputs and modeled machine assumptions. Reachable dangling, incompatible, unaligned, and invalid-representation accesses are excluded faults. Native exception freedom also depends on the resource and foreign-call model. Termination does not imply a stack, heap, or wall-clock bound. [Lean's recursion model](https://lean-lang.org/doc/reference/latest/Definitions/Recursive-Definitions/)

## 6. Project laws

Declare named, typed propositions in `LAWS.aethel`. For example, `law status_round_trip(s: Status) { Status.decode(Status.encode(s)) == Some(s) }`. Resolve laws to the same checked definitions consumed by the compiler. Define truth over logical evaluation and observations, including logical before/after state and typed errors where applicable. A postcondition over returning executions and an assertion of termination have different propositions.

`aethel verify` enumerates all declared laws, elaborates their propositions, and has Lean check proof terms. Use bounded automation and optional hints or a companion Lean proof when needed. Show open goals in source terms, distinguish unproved obligations from demonstrated counterexamples, and fail package verification if any required law lacks evidence. Proofs erase. Recheck when checked definitions or relevant dependencies change. Audit all law evidence transitively and show named foreign contracts on which a theorem depends. Prove foreign-dependent statements by quantifying over a contract, with no project axioms. The initial fixtures cover Status round trip, concrete functional laws, permutation as well as sortedness, and sibling-field preservation under mutation.

Bend 2's `LAWS.bend`, matching proof definitions, and kernel-backed `--verdict` motivate the workflow. Bind proofs to the checked core and track the separate proof obligation for source elaboration and native lowering. [Bend guide](https://github.com/bendlang/bend/blob/0e2f38f759cc830849e489307f3d256a7d148288/guide/GUIDE.md#L319-L332)

## 7. Rust interoperability

Select individual crate functions and concrete types. Generate a Rust adapter crate and compile it with Cargo/rustc as a static system library exposing the target C ABI. Link it through Zig. Start on x86-64 Linux with the installed tools. Rust resolves traits and instantiates generics on its side. Use fixed-width scalars by value, contiguous primitive ranges as pointer plus length, and Rust-owned objects behind opaque affine handles. Pair each owning handle with destruction in Rust. Rich types use explicit adapters. Copy adapters explicitly marshal packed or split data when the API requires a contiguous owned representation.

The checker verifies each borrowed range's live provenance, initialized representation, alignment, bounds, stride, and size within the Rust slice contract. Empty ranges use an explicitly valid empty representation. Shared calls freeze the relevant storage. Mutable calls reserve the entire physical writable range and suspend conflicting handles until return. Two disjoint mutable columns or ranges can be passed together. The first boundary is synchronous, with no retained borrows, callbacks into Aethel, or raw exported Rust-layout containers. Define matching effects, typed errors and modeled abort, and prohibit cross-boundary unwinding. A callable Rust signature certifies neither termination nor a behavioral law. [Rust ABI](https://doc.rust-lang.org/reference/items/external-blocks.html#abi) · [Slice safety](https://doc.rust-lang.org/std/slice/fn.from_raw_parts_mut.html#safety)

## 8. Implementation order and acceptance

1. Complete ownership and liveness preservation in the byte resource kernel. Establish a data-independent static checker and a simulation against independently defined operational rules. Add the small typed functional core, branching, facts, effects, closures, finite iteration, and termination. Develop the law interface against that core.
2. Finish graph transfer, symbolic overlap, function/return-origin checking, layout descriptors, byte representation, and proofs of initialization, checker acceptance, progress, preservation, totality, and proof erasure. Treat this as the sequential formal gate. Prove scoped fork/join and permission restoration separately before enabling parallel operations. Model the Rust boundary in Lean and prove the call-scope guarantees under its stated contracts.
3. After the sequential gate, implement the production lexer/parser, typed elaboration, borrow checking, layout engine, and native lowering through Zig's built-in self-hosted compiler (`-fno-llvm -fno-lld`, without LLVM) using the installed zvm toolchain. Serialize versioned MIR operations, layouts and certificates. The Lean validator must derive or verify facts against actual operations and reject stale or unsupported certificates. Attach alias metadata only for justified byte accesses. Add the law CLI and generated Rust adapters through these interfaces.
4. Maintain 250+ meaningful positive and negative full-language fixtures and check both verdicts and expected execution results. Cover aliasing, reborrows, branch facts, stale facts, ownership transfer, returned views, closure escapes, termination, layouts, variant changes, and foreign calls. Add scoped-parallel fixtures for its separate gate. Component tests supplement this corpus. Run `bash scripts/verify.sh` for every formal increment. Audit theorem dependencies under the pinned Lean 4.35.0 kernel. Keep claims for the model, validator, Zig implementation, and native execution grounded in their respective evidence.

The research manifest pins the upstream systems and the hashes of archived papers. Research adaptations belong in `research/`. Use the locally selected Zig 0.17.0 through zvm when production work becomes eligible.
